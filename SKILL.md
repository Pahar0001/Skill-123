# Переработка сайта: от адреса до проверенного результата

Это не чат и не генератор кода, а порядок работы команды разработки:
разведка → анализ → план → реализация → проверка в браузере → отчёт.
Скрипты в `scripts/` снимают факты с живой страницы. Решения о дизайне и
тексте принимаются глазами по снимкам. Ничто не считается готовым, пока
не открыто в браузере и не проверено взаимодействием.

Скриптам нужны `puppeteer-core` и `sharp`. Ищутся: в папке проекта, откуда
запущены (в студийном репозитории есть), в `SITE_REWORK_PROJECT`, рядом со
скиллом (`npm i puppeteer-core sharp --prefix ~/.claude/site-rework`) и в
глобальных пакетах npm. Папка прогона по умолчанию
`~/.claude/site-rework/runs/<slug>`, своя — `--out`.

## Вход

Бриф — `templates/brief.md`, но можно и свободным текстом. Из него вынуть:

| поле | что делать, если нет |
|---|---|
| URL | без него не начинать — единственный обязательный вопрос |
| Задача | «улучши» без уточнений → пройти воронку UX (`reference/analysis.md`) и предложить сам |
| Референсы | снять через скилл `design-reference`; не копировать, брать принципы |
| Пожелания по стилю | вывести из текущего сайта: сохранять его язык, если не просили менять |
| Ограничения | по умолчанию: не менять контакты, цены, логотип, основной цвет, бэкенд |
| Исходники | искать самому, см. режимы ниже |

**Где исходники.** Адрес `localhost` — проект в текущей папке. Внешний адрес —
`grep` домена по текущей папке и её `deploy/`; нашёлся — это исходники,
правки в них, проверка на локальном сервере, затем на боевом адресе после
выкладки. Не нашёлся — **режим зеркала**: `mirror.mjs` снимает страницу в
верстак, правки идут в `rework.css`, `rework.js` и HTML зеркала, результат —
зеркало для показа плюс патч для переноса. Режим записать в отчёт.

В режиме зеркала: поднять `serve.mjs <папка>/mirror --proxy <адрес оригинала>`
(API и формы уйдут на оригинал, консоль не будет сыпать 404), а снимки
«до» снимать **с нетронутого зеркала** по тому же адресу, что и «после», —
иначе имена файлов не совпадут и `diff.mjs` не сложит пары.

**Среда.** Большие файлы писать инструментом `Write`: длинный heredoc через
Bash на Windows не проходит в аргумент команды. Git Bash подменяет аргументы
вида `/sites/…` на путь внутри своей папки — скрипты это распознают и
исправляют, но надёжнее передавать в `--pages` полные адреса.

## Три правила, которые не обсуждаются

**1. Статике не верить.** `new THREE.Scene()` в коде не значит, что 3D
рисуется; `onClick` не значит, что кнопка работает; `animation:` в CSS не
значит, что движение выглядит хорошо. Всё, что зависит от JS, WebGL,
Canvas, анимаций, наведения, клика, прокрутки, касания и состояния, —
проверяется `runtime.mjs` или браузерным MCP и открывается глазами.
Порядок для любого визуального результата: сделать → запустить → открыть в
браузере → снимок → посмотреть → взаимодействовать → консоль → и только
тогда статус VERIFIED.

**2. Не притворяться.** Пять разных состояний, и они не сливаются:

| состояние | что означает |
|---|---|
| ANALYZED | изучено по снимкам, DOM, коду |
| IMPLEMENTED | код написан, страница открывается |
| RUNTIME VERIFIED | в браузере произошло ожидаемое: нет ошибок, клик/скролл/холст дали результат |
| VISUALLY VERIFIED | снимок открыт глазами на нужных экранах и выглядит как задумано |
| PERFORMANCE VERIFIED | измерено `perf.mjs`, бюджеты соблюдены или отклонение записано |

Каждая задача живёт в `state.mjs` с пятью статусами. В отчёт идёт только
то, что реально проверено; непроверенное так и называется. «WebGL проверен»
без открытого холста, «mobile готов» без снимка на 390 px, «оптимизировано»
без замера — запрещённые фразы.

**3. Минимум достаточных инструментов — но без отказа от сложных.**
Простая правка CSS не требует Lighthouse; сцена на Three.js требует
холста, снимка, замера кадров и телефона. Выбор — по `reference/tool-registry.md`.

И четыре правила поменьше: **ничего не выдумывать** (цены, сроки, отзывы,
факты о бизнесе — только с сайта или от пользователя); **референсы не
копировать** (принципы — да, тексты, картинки, структура целиком — нет);
**тексты — для читателя сайта**, не для разработчика, без жаргона и без
«AI-копирайтинга»; **о мелочах не спрашивать** — спрашивать только там, где
разные ответы ведут к разной работе (см. «Когда спрашивать»).

## Порядок работы

Этапы отмечать в журнале: `node scripts/state.mjs <папка> stage <этап> done`,
и показывать пользователю чек-лист (`state.mjs show`) при каждом переходе.

### 0. Подготовка

```
node scripts/state.mjs <папка> init <url> "<запрос>"
```
Определить режим (исходники / зеркало). Локальный проект — поднять сервер
(`npm run dev` или что есть в `package.json`). Записать ревизию инструментов
в `<папка>/tools.md` по чек-листу из `reference/tool-registry.md`: что
доступно, что требует авторизации, какие fallback.

### 1. Разведка — состояние ANALYZED

```
node scripts/discover.mjs <url>                      # техника, содержимое, визуал, снимки, дизайн-система
node scripts/runtime.mjs <url> --scroll --canvas --motion --fullpage
node scripts/runtime.mjs <url> --viewport mobile --scroll --click "<переключатель меню>" --shot menu
node scripts/perf.mjs <url>                          # телефон, медленная сеть — база для сравнения
node scripts/a11y.mjs <url> --viewport mobile
node scripts/shots.mjs <url> --tag before --pages /,<другие страницы в задаче>
```
Заставки и прелоадеры скрипты ждут до 5 с и записывают в разведку
(«заставка при загрузке: …, ушла через N мс»); если не ушла — это находка.
Прочитать `discovery.md`. **Открыть снимки** (`Read` показывает PNG): первый
экран и всю страницу на desktop и mobile, серию по прокрутке. Заполнить
визуальный разбор словами по `reference/discovery.md` — язык дизайна,
иерархия, приём, что сильное и сохраняется. Переключатели меню и слайдеры
брать из раздела «интерактив» разведки и прогонять кликом.

Референсы: `design-reference` (`extract.mjs` на каждый) → сравнить с
основным сайтом → выписать принципы, а не элементы.

Что выяснить на выходе: платформа и ограничения (Tilda, WordPress, свой код),
что уже хорошо, что сломано (P0), как сайт зарабатывает (звонок, заявка,
корзина) и где на этом пути трение.

### 2. Анализ и план

По `reference/analysis.md`: разобрать запрос на области (UI, UX,
типографика, тексты, картинки, движение, 3D, навигация, формы, телефон,
скорость, SEO, доступность, структура), составить матрицу **менять / не
трогать**, пройти воронку Arrival → Understanding → Interest → Trust →
Decision → CTA → Conversion и найти трение. Каждое решение — с причиной.

План — задачи в журнале с приоритетом:

```
node scripts/state.mjs <папка> add "Меню на телефоне не открывается" --priority P0 --area mobile
```
P0 сломано · P1 крупная проблема UX · P2 крупная визуальная · P3 тексты ·
P4 движение · P5 полировка. Порядок: P0 → P5, внутри — зависимости:
дизайн-система раньше UI, тексты раньше подгонки вёрстки, картинки раньше
секций, которым они нужны, 3D и движение после того, как вёрстка встала.

Выбрать инструменты под задачи (`reference/tool-registry.md`) и записать
в план: чем именно будет сделано и чем проверено.

### 3. Реализация — по одной задаче

Для каждой задачи: сделать → перезагрузить → `runtime.mjs` с шагами именно
под неё → снимок → открыть глазами → исправить → повторить. Не принимать
первый результат: минимум один круг исправлений на каждую заметную задачу.

- вёрстка и UI: правки в дизайн-системе сайта (переменные из `design/site.tokens.css`),
  не поверх; без новых сборщиков и фреймворков на сайте, где их нет;
- тексты: `reference/analysis.md`, раздел «Тексты»;
- картинки: `reference/engines.md` → «Картинки» (переиспользовать → отредактировать → сгенерировать);
- 3D: `reference/engines.md` → «3D»: сначала ответ «нужно ли», потом подход, потом обязательная проверка холста;
- движение: `reference/engines.md` → «Движение»: CSS первым, библиотека — только когда без неё нельзя, `prefers-reduced-motion` всегда;
- телефон: отдельная вёрстка первого экрана, меню, форм и таблиц, а не «ужать десктоп».

После каждой задачи:
```
node scripts/state.mjs <папка> set <id> impl=DONE runtime=VERIFIED visual=VERIFIED --note "что проверено"
```

### 4. Проверка — по `reference/qa.md`

```
node scripts/shots.mjs <url> --tag after --pages <те же>
node scripts/diff.mjs <папка>/before <папка>/after       # где изменилось — совпадает ли с планом; при смене высоты — колонка «со сдвигом»
node scripts/runtime.mjs <url> --scroll --canvas --motion --click ... --type ...   # desktop и mobile
node scripts/perf.mjs <url> --runs 3                     # медиана трёх прогонов против базы
node scripts/a11y.mjs <url> --viewport mobile            # контраст и на картинках — по снимку фона
```
Холст проверяется по снимкам (с холстом и со спрятанным холстом) и ждёт до
4 с, если 3D стартует лениво; чтение буфера WebGL — подробность, не приговор.
Сдвиги вёрстки ищутся наблюдателем, поставленным до скриптов страницы
(`runtime.mjs --init …`, рецепт в `reference/qa.md`).
Открыть глазами все `after/*-first.png` и `*-full.png` на desktop, tablet,
mobile и все `diff/*.png`: изменения только там, где планировались; что
должно было сохраниться — сохранилось. Функциональное: все ссылки, кнопки,
меню, формы, слайдеры — через шаги `runtime.mjs`. Ошибок в консоли ноль.

Условие выхода из цикла: все P0–P2 в статусе VERIFIED по runtime, visual
и mobile; `perf` не хуже базы; `a11y` без FAIL; иначе — ещё круг. Если
круги закончились по времени — оставшееся честно в отчёт.

### 5. Отчёт — `templates/report.md`

Обязательные разделы: сайт, запрос, что изучено, инструменты и зачем,
изменения, проверено в браузере, проверено глазами, скорость (цифры до и
после), что осталось, рекомендации. Таблица задач — из `state.mjs show`.
Пути к снимкам «до/после» и diff — в отчёт, чтобы пользователь открыл сам.

## Прогресс для пользователя

При каждом переходе между этапами показывать чек-лист из `state.mjs show`:

```
✓ Сайт разведан
✓ Открыт в браузере, консоль и сеть сняты
→ Дизайн разобран глазами
· План с приоритетами составлен
```
Между этапами — короткие строки: что делается, что нашлось. Без пересказа
файлов и без обещаний того, что не проверено.

## Когда спрашивать, а когда решать самому

Спрашивать (через `AskUserQuestion`, если сессия интерактивная; иначе принять
допущение, записать его в отчёт и продолжать):
- запрос конфликтует с ограничением («сделай ярче» при «не менять основной цвет»);
- генерация картинок или 3D стоит денег на счету пользователя (Higgsfield);
- удаление секций, смена цен, контактов, юридических текстов;
- две трактовки ведут к разным сайтам (например, «дороже» = минимализм или = тёмная роскошь), и референсов нет — тогда предложить два направления одним вопросом.

Не спрашивать: размеры отступов, выбор гарнитуры в рамках текущего языка,
длительности анимаций, порядок секций внутри плана, формулировки текстов —
сделать, показать снимком, поправить по отклику.

## Восстановление после сбоев

Не останавливаться на первом отказе; но в отчёте — что именно не проверено.

| отказало | дальше |
|---|---|
| `scripts/*.mjs` (нет puppeteer-core, браузер не поднялся) | `SITE_REWORK_PROJECT`, `CHROME_PATH` → chrome-devtools MCP → playwright MCP → пометить UNVERIFIED |
| Edge завершился молча | поставить Chrome первым (уже так) или `CHROME_PATH` на Chrome |
| `sharp` не найден | `diff.mjs` пропустить, сравнивать снимки глазами; картинки не пережимать |
| `design-reference` нет рядом | палитра и шрифты из `discovery.md`, токены выписать руками |
| генерация картинок недоступна (нет кредитов, нет авторизации) | SVG/CSS-графика, фото по свободной лицензии (Openverse, смотреть глазами), оставить существующие |
| нет модели для 3D | процедурная геометрия в Three.js, частицы, шейдер — не ждать модель |
| сервер отдаёт 429 | подождать минуту, не перезапускать |
| `net::ERR_TIMED_OUT`, `ERR_CONNECTION_RESET` при открытии (медленное TLS-рукопожатие, нестабильный сервер) | скрипты сами повторяют переход трижды и пишут WARN «открылось с N-й попытки»; проверить `curl -w '%{time_appconnect}'`; не гонять несколько скриптов по такому сайту параллельно; если не открывается совсем — chrome-devtools MCP `new_page` с таймаутом 120 с |
| страница за логином, зеркало не снимается | попросить доступ или исходники; работать по снимкам пользователя как ANALYZED |

## Файлы скилла

```
scripts/lib.mjs        браузер, экраны, журнал страницы, папка прогона
scripts/discover.mjs   разведка: техника, содержимое, визуал, снимки, дизайн-система
scripts/runtime.mjs    проверка в браузере: консоль, холсты, анимации, наведение, клик, ввод, прокрутка
scripts/shots.mjs      снимки «до/после» на одинаковых экранах с остановленным движением
scripts/diff.mjs       где изменилась картинка: доля, полосы, картинка различий
scripts/perf.mjs       скорость с бюджетами: LCP, CLS, вес, кадры/с, память
scripts/a11y.mjs       контраст, alt, подписи, фокус, цели нажатия, reduced-motion
scripts/state.mjs      журнал задач и этапов с пятью статусами
scripts/mirror.mjs     зеркало чужой страницы как верстак (rework.css / rework.js)
scripts/serve.mjs      статический сервер для зеркала; --proxy отдаёт остальное оригиналу
reference/tool-registry.md   что есть, когда чем пользоваться, чем заменять
reference/discovery.md       визуальный разбор словами, дизайн-система, референсы
reference/analysis.md        разбор запроса, матрица менять/сохранять, воронка UX, тексты, приоритеты
reference/engines.md         картинки, 3D, движение, телефон, правила реализации
reference/qa.md              проверки: runtime, визуал, функции, телефон, скорость, доступность, регресс
templates/brief.md           форма запроса
templates/report.md          форма отчёта
ui/brief-form.html           форма в браузере, собирает текст брифа
```
