# Безопасность и утечки

Сайты боевые, с формами и админками. Одна открытая служебная папка, форма с
телефоном методом GET или ключ в коде страницы — это уже утечка, а не «некрасиво».
Проверка `security.mjs` меряет это фактами по HTTP и по коду: не «взлом», а гигиена.
Значения ключей и куки в выводе и в протоколе **всегда замаскированы**.

Запускать на финальном проходе для **каждого** сайта (шаг §4 в `SKILL.md`), а также
сразу, если правки касались форм, админки, заголовков сервера или сторонних скриптов.

## Команды

```
node ~/.claude/skills/site-rework/scripts/security.mjs <url> --out <папка> --tag <имя> \
     --repo <папка исходников> --admin /admin,/api/admin/…
node ~/.claude/skills/site-rework/scripts/security.mjs <boевой-url> --out <папка> --tag prod   # без --repo
node ~/.claude/skills/site-rework/scripts/security.mjs --repo <папка> --out <папка>            # только исходники
node ~/.claude/skills/site-rework/scripts/security.mjs --selftest
```

Проверять и **локальный** адрес (за ним видно код и репозиторий), и **боевой** —
заголовки безопасности часто ставит прокси (Caddy/nginx), а не приложение, и на
`localhost` их нет: локальный прогон покажет по ним WARN, боевой — как на самом деле.
Только чтение, запросы идут вежливо (пауза между ними), без нагрузки и перебора.

## Вердикты

`OK` — проверка пройдена. `WARN` — подозрительно или требует решения (счётчик,
слабый CSP, форма без явного метода). `FAIL` — утечка или дыра (открытый файл,
данные без входа, секрет в коде, GET с личными данными). Итог — худший из вердиктов;
код выхода 1 только с `--strict` и при FAIL. Протокол — `<out>/security/<tag>.json`
(поле `lines` со статусами, `verdict`); его читает `state.mjs` как доказательство.

## Что проверяется по адресу сайта

- **Служебные файлы (a).** `/.env(.local/.production)`, `/.git/HEAD` и `/config`,
  резервные копии и базы (`*.zip`, `*.sql`, `*.sqlite`, `*.db`, `*.bak` в корне и в
  `data/`, `backup/`), исходники (`/server.js`, `/package.json`, `/src/…`), карты
  `*.map` найденных скриптов, листинг папок. FAIL — только если отдаётся **содержимое**
  файла: тело сверяется с телом страницы 404 (её снимаем случайным адресом) и с приметами
  формата, поэтому SPA-заглушка с кодом 200 за файл не считается.
- **Админка и API без входа (b).** Пути из `--admin` и найденные на странице
  (`/admin`, `/api/admin/…`). Закрытые данные без входа (200 и JSON не про ошибку
  авторизации) — FAIL. Страница входа с полем пароля или 401/403 — OK.
- **Формы (c).** `method=get` с полем имени, телефона, почты или пароля — FAIL
  (личные данные уедут в адрес и в журналы сервера). Метод не указан — WARN (по
  умолчанию GET; чаще сабмит перехватывает JS — убедиться). Поле пароля по http (не
  localhost) — FAIL. Отправка на чужой домен или по http — WARN.
- **Секреты в коде страницы (d).** Ключи AWS, Google API, Stripe, Slack, GitHub, токен
  Telegram-бота, приватные ключи, JWT, присваивания `api_key`/`secret`/`password`/`token`
  со значением, `Authorization: Bearer` — в HTML и в скриптах своего источника. FAIL со
  строкой, значение замаскировано. В тестовых и примерочных файлах (`tests/`, `*.test.*`,
  `*.example`) общие правила молчат — там пароли-фикстуры; форматные ключи ловятся везде.
- **Сторонние запросы (e).** Чужие домены из разметки, скриптов и CSP. Счётчик или
  реклама, **подключённые** на странице — WARN (данные уходят третьим лицам — в политику
  конфиденциальности); чужой `iframe` — WARN. Домен, только **разрешённый в CSP**, но на
  странице не подключённый, — отдельная строка: лишнее разрешение можно вычистить (часто
  остаток от убранного виджета). Список статический: что подгрузит уже сам чужой скрипт в
  браузере, здесь не видно — это сказано в выводе.
- **Заголовки безопасности (f).** `Content-Security-Policy` (и слабость `'unsafe-inline'`/
  `'unsafe-eval'`), `X-Content-Type-Options: nosniff`, `X-Frame-Options` или CSP
  `frame-ancestors`, `Referrer-Policy`, `Strict-Transport-Security` (на https),
  `Permissions-Policy`; куки сессии — `HttpOnly`, `Secure` (на https), `SameSite`;
  смешанное содержимое (http-ресурс на https-странице).

## Что проверяется в `--repo`

- **Секреты (g).** `gitleaks` по истории, если установлен (`winget install
  gitleaks.gitleaks`), иначе свой поиск по образцам (до 500 коммитов). Плюс всегда свой
  поиск по отслеживаемым файлам (`git ls-files`, без `node_modules`). `.env` отслеживается
  git — FAIL (удалить из индекса и сменить все ключи из него); `.env` не в `.gitignore` —
  WARN. Значения замаскированы. `RW_SEC_NO_GITLEAKS=1` — заставить свой поиск (для selftest).

## Пределы

- Список сторонних запросов — статический (разметка + CSP). Ресурс, который в браузере
  подгружает сам чужой скрипт, в него не попадает.
- Секреты ищутся по образцам известных форматов и присваиваниям — не по энтропии; ключ
  необычного вида может не опознаться. `gitleaks` по истории надёжнее — ставить его.
- Проверяются страницы, переданные адресом; скрытые маршруты и вебхуки — руками.

## Selftest

`--selftest` поднимает на свободных портах два стенда (`fixtures/security/vuln` — с
нарочными дырами, `fixtures/security/clean` — без) и временный репозиторий с секретом в
истории и `.env` под git; ожидания — на каждый пункт a–g. Зелёный selftest — условие
перед коммитом скилла. Правил и стендов касается `fixtures/security/README.md`.
