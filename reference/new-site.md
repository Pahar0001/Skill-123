# Сайт с нуля по требованиям

Когда: «сделай сайт с нуля», «вот ТЗ», «вот PRD», донора нет. Требования приходят не одним
брифом, а по ходу: сообщения, файлы (.docx, .pdf), голосовые, скриншоты, ссылки. Своего «до»
нет, донора нет; эталон — направление, которое выбрал пользователь, и критерии требований.
Сайт собирается в `<папка>/site`.

Журнал:
```
node ~/.claude/skills/site-rework/scripts/state.mjs <папка> init - "<запрос одной строкой>" --mode new --site <папка>/site   # «-» — адреса ещё нет; папку site init создаст сам
node ~/.claude/skills/site-rework/scripts/state.mjs <папка> meta --url http://localhost:<порт>/     # когда сайт поднят serve.mjs
```
Папку прогона называть по проекту (`runs/kinokomnata`), а не по адресу: адрес локальный и меняется.
Первой строкой `analysis.md` — «режим: с нуля; сайт собирается в <путь>; требования — requirements.md».
С донором — это режим донора (`reference/donor-mode.md`), реестр требований работает поверх него
так же.

**Реестр требований в режиме `new` обязателен** (`state.mjs show` без него — WARN), в остальных
режимах — как только источников требований больше одного (второе сообщение с пожеланиями, файл ТЗ
к брифу, голосовое): `state.mjs <папка> stage requirements active` и дальше так же.

## 1. Требования — в реестр, с цитатой

Каждое сообщение, файл, голосовое, скриншот, где пользователь чего-то хочет, — источник:

```
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> ingest --file "<ТЗ.docx>"                 # таблицы — по столбцам
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> ingest --text "<сообщение>" --said "<когда>"
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> ingest --file "<скрин.png>" --note "<что он сказал о нём, дословно>"
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> ingest --file "<ТЗ v2.docx>" --supersedes S-001   # новая версия документа: что добавлено, изменено, пропало
```

- **.pdf** — `pdftotext` (есть в Git), иначе `pypdf`; не вышло — `Read` глазами, текст `--text`,
  файл `--original`; цитата с номером страницы (`--loc "стр. 3"`), в реестре — пометка «из PDF».
- **Голосовое** — сначала расшифровка:
  `PYTHONIOENCODING=utf-8 "D:/tools/whisper/venv/Scripts/python.exe" "D:/tools/whisper/transcribe.py" "<файл>" --out "<папка>/requirements/sources"`,
  потом `ingest --file <расшифровка.md> --kind voice --original <файл>` (аудио `ingest` сам не берёт
  и печатает эти команды). Длинное (от 10 минут) — `D:/tools/whisper/run_batch.ps1` отдельным
  процессом. Место, где распознавание сомнительно (имя, цифра, цена), — переспросить, не угадывать:
  цитата из расшифровки помечена «voice».
- **Скриншот** — открыть `Read`, требования сформулировать самому; цитата — слова пользователя о
  картинке (`--note` источника), без них цитировать нечего.
- **Ссылка** — `ingest --url <адрес> --note "<что нравится>"`; это референс или донор (§3).
- **Вложение «не пришло»** — сначала `ls -lt ~/Downloads | head`: файл обычно уже там.

`ingest` печатает кандидатов c01… с цитатой и местом в документе и помечает шум. Решение — за
моделью, по оригиналу:

```
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> add --from S-001 --take 24,25 --page / --block search
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> add --from S-001 --take 15 --to R-001        # тот же смысл из другого места — второй источник
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> add --from S-001 --dismiss 3-5,23,32 --why "метаданные, примеры шаблона"
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> add "Тёмная тема, как в кинозале" --source S-002 --quote "тёмный как зал" --kind style
```

**Атом** — одна вещь, которую можно проверить одним критерием. «Поиск и фильтры по жанру и
рейтингу» — три требования; «тёмный, без градиентов, и чтобы на телефоне всё влезало» — `style`,
`constraint`, `page`; «Код комнаты уникален, ключи API не видны пользователю» — два (кандидат —
`--dismiss --why "составной"`, атомы — `add … --quote "<кусок строки>"`). Номер из документа
(FR-01) сохраняется: пользователь говорит на его языке.

**Цитата обязательна**: требования без цитаты-источника не существует. `add` ищет её в тексте
источника и без неё не пишет; своя формулировка — только перефразирование, смысл — словами
пользователя.

**Шум документа не импортировать**: примеры из шаблона (в PRD «КиноКомнаты» — «Страница
расписания… при 100 одновременных пользователях», «Доля успешных сценариев записи»: расписания в
проекте нет), «Заполнить», пустые таблицы, метаданные. ФИО участников (чужие личные данные)
`ingest` снимает сам — ни в реестр, ни в отчёт. Не взятое — `--dismiss` с причиной, список — в
отчёт. Если без сомнительной строки меняется план — спросить.

**Контекст — не задачи**, но работает (виды `about`, `glossary`, `audience`, `risk`,
`assumption`, `schedule`): о чём продукт — основа текстов и вопроса «о чём сайт»; глоссарий —
одни и те же слова во всех текстах сайта («Комната», «Совпадение»); аудитория — в воронку; риски и
предположения — в отчёт.

**Приоритет** — из документа (Must/Обязательно → must); из чата — по словам («обязательно»,
«нужно», «должна» → must; «хорошо бы» → should; «было бы неплохо» → could); иначе своё: must для
того, без чего сайт не выполняет главное действие, остальное — should (`change … --priority …
--self --why`).

**Критерий у каждого** (`accept`), выбирается сразу, а не в конце. `add` подсказывает критерий
по умолчанию для вида:

| вид | критерий по умолчанию | доказательство |
|---|---|---|
| функция | сценарий кликом и вводом, утверждение результата, desktop и 390 | `runtime` + `mobile`, `--assert "/*R-x.a*/ …"` |
| страница | открывается без ошибок; h1 и главное действие выше сгиба на 390; снимки desktop, 390, 320 | `runtime`, `eye` |
| текст, факт | стоит на месте; факт — дословно как у пользователя | `runtime --assert`, `eye` |
| стиль | как выбранное направление; числа спецификации; без шаблона | `eye` (пара снимков), `verify`, `cliche` |
| «не делать» | приёма нет | `cliche` без правила, `runtime --assert` отсутствия |
| движение | вид и числа по паспорту; «меньше движения» | `motion`, `runtime --reduced-motion` |
| кадры | по смыслу, лицензия записана | `eye`, `credits.json` |
| скорость | порог из требования («до 2 с» → LCP ≤ 2000 на телефоне, fast3g, ×4, медиана трёх) — допущение в отчёт | `perf --metric "LCP<=2000"` |
| доступность | без FAIL | `a11y` mobile и desktop |
| браузеры | Chrome и Firefox; Edge на этой машине без окна не запускается | `browser` (`runtime --browser firefox`); Edge — `manual` |
| безопасность | ключа нет в HTML, JS и адресах запросов | `runtime --assert` |
| форма, ПДн | согласие и политика рядом с отправкой; тексты — от пользователя | `runtime`, `eye` |
| сервер, нагрузка, доставка письма | здесь не проверить | `manual` с причиной — в «Не проверено» |

```
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> accept R-001 --add "runtime: поиск «Матрица» показывает карточки с этим словом" --how "runtime.mjs {url} --out {run} --tag r001 --type \"[data-search]=Матрица\" --assert \"/*R-001.a*/ document.querySelectorAll('[data-film]').length>0\""
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> accept R-009 --add "perf: LCP до 2 с на телефоне" --metric "LCP<=2000" --how "perf.mjs {url} --out {run} --tag r009 --runs 3"
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> accept R-011 --add "manual: Edge" --reason "Edge 153 без окна молча падает на этой машине"
```

Маркер `/*R-007.a*/` стоит в начале утверждения. Он попадает в подпись шага протокола, и
доказательство находится само (самый новый протокол в `<папка>/runtime` с этим шагом; для `mobile`
— снятый на экране уже 1024 px, для `browser` — в Firefox); в журнал —
`--evidence 'runtime/r007.json#/*R-007.a*/'` (в Bash — в одинарных кавычках). `{url}` и `{run}` в
`--how` подставляет `checks`. Снимок для `eye` прикладывается после взгляда:
`accept R-… --evidence b after/home-mobile-first.png`.

## 2. Что спросить, что решить самому

**Спросить** — одним сообщением, с вариантами, и только там, где разные ответы дают разный сайт:

1. о чём сайт и что продаёт, если этого нет в источниках — без этого не начинать (`check` в режиме
   `new` без требования вида `about` — WARN);
2. главное действие посетителя (заявка, звонок, покупка, запись, регистрация), если оно не следует
   из требований;
3. язык сайта: есть донор или референсы — или показать направления (§3);
4. **веб-сервис с серверной частью** (комнаты, чат, вход, общие данные, оплата): делать ли демо —
   варианты «демо в браузере с пометкой «демо»», «готовый сервис (аккаунт и ключ пользователя)»,
   «сервер — отдельная работа»; `conflicts` печатает готовую команду `ask`;
5. стек, если ТЗ его требует и он меняет работу (Next.js — сборка и сервер разработки; Tilda —
   другой инструмент);
6. противоречие двух требований из одного источника; сомнительная строка документа, от которой
   зависит план;
7. платная генерация — с суммой (`recraft.mjs` без `--yes`, Higgsfield);
8. новое пожелание про вид сайта — только этот сайт или все (WISHES.md), если непонятно.

**Факты** (цены, контакты, адрес, реквизиты, отзывы, тексты согласия и политики) не выспрашивать по
одному и не выдумывать: в вёрстке `[уточнить: …]`, список «Ждём от вас» (`report`) — одним
сообщением после плана и в отчёте. Цены, сроки, гарантии — только подтверждённые пользователем.

**Решать самому** и записывать допущение: разбиение на атомы, критерии, трактовку размытого
(«быстро», «удобно»), приоритет внутри must, состав страниц в рамках требований, раскладку и шкалу
внутри выбранного направления, гарнитуру внутри направления (с проверкой кириллицы), тексты по
правилам `analysis.md` → «Тексты», кадры из законных источников, что из документа — шум (со списком
в отчёте).

**Нет связи с пользователем** (сессия не интерактивная) — вопросы не ждут ответа: `ask …` и сразу
`assume Q-… "<вариант, который меньше всего придётся переделывать>"`, работать дальше; вопросы и
допущения — в отчёт первыми. Для веб-сервиса это **демо с явной пометкой «демо»**: данные живут в
браузере (localStorage, между вкладками — BroadcastChannel), пометка рядом с действием и в подвале
— одна на место, не россыпью (`cliche.mjs`, правило `demo-badges`); серверные критерии — `manual`.

## 3. Язык сайта

**С донором** — `reference/donor-mode.md` целиком. Реестр — поверх: страницы донора, которые
подходят по смыслу, — требования вида `page` с решением `question` до ответа; стиль, который спорит
с паспортом донора, — `conflicts` (тип `passport`) → вопрос.

**С референсами — 2 направления.** `design-reference/scripts/extract.mjs <референс> --out
<папка>/refs --name <имя>` на каждый; из каждого — 1–3 **принципа** с числом («воздух: отступ
секций 160–200 px при h2 56 px»), требование вида `reference` с цитатой «что нравится». Референс —
не донор: вёрстка не сверяется с ним `verify.mjs`, тексты, кадры и структура не берутся.
Направления строятся из принципов.

**Без донора и референсов — 3 направления** до сборки страниц:

1. **Откуда направления.** Не из «стилей» вообще, а по трём осям, по одной на направление:
   (а) предмет отрасли — как выглядит мир заказчика (кинокомната: билет, афиша, титры, тёмный зал);
   (б) задача сайта — что человек делает и как сделать это короче (инструмент: поиск и результат с
   первого экрана); (в) принятое пользователем раньше (`taste.mjs brief` — эталоны) и свежая идея
   банка (`ideas.mjs pick --run <папка> --for "<о чём сайт>"`).
2. **Паспорт каждого** — `<папка>/direction/<a|b|c>/passport.md`: восемь вопросов
   `reference/authorship.md` §2 (текст на фоне, линия, кнопка, фото, заголовок, пустота, движение,
   фактура) и раздел «Никогда» — 5 правил списком (его читает `requirements.mjs conflicts`, тип
   `passport`). Направления различаются **не меньше чем в трёх** из восьми ответов — иначе это одно
   направление в разных цветах. Гарнитура — с кириллицей (`design-reference/scripts/cyrillic-check.mjs`),
   пара для заголовков и текста; палитра — с контрастом текста ≥ 4.5:1.
3. **Эскиз каждого** — `<папка>/direction/<x>/index.html`: первый экран и один ключевой блок, в
   котором больше всего требований (карточка, форма, результат поиска), с настоящими словами из
   реестра, без выдуманных фактов (`[уточнить]`). Отдавать эскизы `serve.mjs <папка>/direction
   --port 43xx`: модули (`type=module`, Three.js) с `file://` браузер не грузит. Снимки desktop и
   390 — `shots.mjs http://localhost:43xx/<x>/ --out <папка>/direction/<x>`; шаблонность —
   `cliche.mjs http://localhost:43xx/<x>/ --taste --run <папка> --json <папка>/cliche/direction-<x>.json`:
   без базы каждое правило веса 3 либо убрать, либо записать причину (задача блока) в
   `authorship-decisions.json`.
4. **Показать до сборки**: снимки рядом, по строке на направление — идея и чем отличается. Выбор
   пользователя — `requirements.mjs <папка> direction <x> --quote "<его слова>"` и
   `taste.mjs add --block direction --verdict preferred --by user --quote "<его слова>" --run <папка> --img <снимок>`;
   отвергнутое — `rejected` с его словами. Автономно — `direction <x> --self --why "<почему по
   требованиям>"`, в отчёте — все эскизы и причина.
5. **Выбранное — свой донор**:
   ```
   node ~/.claude/skills/design-reference/scripts/extract.mjs http://localhost:43xx/<x>/ --out <папка>/direction/design --name direction
   node ~/.claude/skills/site-rework/scripts/cliche.mjs baseline http://localhost:43xx/<x>/ --out <папка>/cliche/direction.json
   ```
   Токены `direction.tokens.css` → переменные сайта; дальше — как в режиме донора: `verify.mjs` по
   `direction.json`, `cliche.mjs --baseline <папка>/cliche/direction.json`. База шаблонности
   снимается только с эскиза, который прошёл шаг 3: иначе свой дефолт узаконит сам себя.
   `state.mjs <папка> stage direction done`.

Движение без донора — из паспорта направления («как движется»), 1–2 из самого товара и 1–2 из банка
идей (`reference/motion.md`); `motion.mjs <наш url> --tag site` — инвентарь для отчёта; `compare`
не с чем.

## 4. Требования → план

Порядок разбора — сверху вниз, каждая строка ссылается на требования:

1. **Страницы** — из требований вида `page` и из функций, которым нужна своя страница; нет в
   требованиях — предложить состав одним вопросом (для магазина: главная, товар, корзина; для
   сервиса: главная, экран работы, справка).
2. **Блоки** на каждой странице — у каждого активного требования `--page` и `--block` (раскладка —
   своя: `change R-… --page … --block … --self --why "раскладка"`, редакция не меняется).
3. **Компоненты**, которые повторяются (карточка, форма, фильтр), — по паспорту направления; чего в
   паспорте нет — `reference/authorship.md` §3–4.
4. **Тексты и факты** — `analysis.md` → «Тексты», глоссарий из реестра, `[уточнить]` там, где факта нет.
5. **Интеграции** — API, отправка формы, почта, аналитика: по решению из §2 (настоящее или демо с пометкой).
6. **Задачи** — одной командой задача в журнал и связь с требованиями:
   ```
   node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> plan R-001,R-002 "Поиск и фильтры на главной" --area search
   node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> report --plan      # таблица «требование → страница/блок → задача → критерий» — в analysis.md
   ```
   Приоритет задачи по умолчанию — из требований: must-функция, страница, факт — P1; must-стиль и
   кадры — P2; тексты — P3; движение — P4; should — на ступень ниже; could — P5. Сломанное (P0)
   появляется при проверке. Задача без требования допустима (трение воронки, правило донора, P0
   разведки), требование без задачи — нет.

`requirements.mjs <папка> list --open` пуст — план готов: у каждого активного требования задача и
критерий. `conflicts` — пуст или каждый пункт — вопрос с ответом или допущением, либо `ack` с причиной.

## 5. Сборка и проверка

Как `SKILL.md` §3–4; отличие — критерии уже известны. Для каждой задачи: сделать →
`runtime.mjs` с утверждениями её критериев (`--assert "/*R-001.a*/ …"`) → снимок → глазами →
поправить. Скрипт всех проверок собирается из реестра:

```
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> checks --sh <папка>/checks.sh     # адрес — из state.mjs meta --url или --url
bash <папка>/checks.sh                         # по одной проверке за раз: скорость не мерить параллельно
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> checks --journal <папка>/journal.sh   # после прогона: set по найденным протоколам
bash <папка>/journal.sh                        # runtime, mobile, perf — в журнал; visual — руками, после взгляда на снимок
node ~/.claude/skills/site-rework/scripts/requirements.mjs <папка> report
```

## 6. Пришло новое требование

1. **Записать сразу**, даже посреди задачи (довести её до места, где сайт открывается): `ingest`.
2. **Атомы**: новое — `add`; уточнение прежнего — `change R-… --quote "<его слова>"` (редакция +1,
   `needsReview`); отмена — `status R-… dropped --quote "<его слова>"`; замена — новое `add` и
   `status <старое> superseded --by <новое>`. Последнее слово пользователя решает, но старое не
   исчезает: история — в реестре и в отчёте. Не уверен, что это — `impact --text "<сообщение>"`
   покажет похожие требования и полярность, ничего не записывая.
3. **Противоречия**: `conflicts R-…`. Вопрос — только если ответы ведут к разной работе; новое от
   пользователя позже старого — замена без вопроса.
4. **Влияние**: `impact R-…` — задачи (переоткрыть: `state.mjs set <id> impl=DOING --note "R-…
   ред. 2: …"`, снять: `impl=DROPPED`, новые: `plan`), страницы, блоки, доказательства. Изменение
   требования само делает устаревшими доказательства связанных задач (`state.mjs show` — «требование
   изменено», итог FAIL). Задачи пересмотрены — `link`/`plan`/`review R-… --note "…"`.
5. **Широта правки**: `style`, `motion`, `media`, `reference` и всё, что задевает паспорт направления,
   — это весь сайт: пересобрать спецификацию направления (`extract.mjs`), базу `cliche`, проверить
   все страницы; сказать пользователю, что правка широкая, до того как делать. Функция или текст —
   только свои страницы.
6. **Проверить**: быстрый круг — `checks --only R-… --sh <папка>/quick.sh`; перед сдачей — весь
   `checks.sh`: любая правка файлов сайта делает прежние доказательства устаревшими, это и есть
   проверка на регресс.
7. **Сказать пользователю** в трёх строках: что пришло → что изменилось (задачи, страницы) → чем
   проверено.

Пример (КиноКомната): «чат пока не надо, вместо него кнопка поделиться ссылкой на комнату» → R-008
`dropped` с цитатой, новое требование «Поделиться ссылкой»; задача «Чат» снята, «Комната»
переоткрыта (раскладка без чата), новая — «Поделиться»; `checks --only <новое>,R-005`.

## 7. Сверка перед отчётом

- `requirements.mjs <папка> report`: у активных must нет «без доказательства», «устарело», «нет
  задачи», «нет критерия», «провалено»; `manual` — с причиной; `check` без FAIL;
- `conflicts` пуст или каждый пункт — вопрос в отчёте (с ответом или допущением) либо `ack` с причиной;
- `verify.mjs <папка>/direction/design/direction.json <url>` на каждой странице; `cliche.mjs --baseline
  <папка>/cliche/direction.json --taste --run <папка> --shot`; пары снимков эскиз / страница глазами;
- остальное — `SKILL.md` §4 и `reference/qa.md` → «Условие завершения».

## 8. Отчёт

`templates/report.md` + раздел «Требования» из `requirements.mjs <папка> report --md <файл>`:
таблица (требование, источник и дата, приоритет, задачи, критерии, статус), что не взято из
документов и почему, вопросы с ответами и допущениями, «Ждём от вас», «Не проверено здесь», история
изменений. «Запрос» в отчёте — первое сообщение и список источников, а не пересказ.

## Сайт или веб-сервис

Если требования описывают сервис (комнаты, чат, вход, общие данные, как PRD «КиноКомнаты»), скилл
делает интерфейс и проверяет его в браузере. Делать ли демо — решение пользователя (§2, пункт 4);
нет связи — демо с явной пометкой «демо». Демо-слой в браузере (localStorage, BroadcastChannel
между вкладками) помечается «демо» рядом с действием и в подвале. Серверные критерии («ошибки не
приводят к потере комнаты», «код комнаты уникален», «сообщения видны у других участников»,
нагрузка) — `manual` или `out` словами пользователя, в отчёт как не проверенные здесь. Назвать демо
готовым сервисом нельзя.
