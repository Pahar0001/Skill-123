# Анализ запроса, воронка UX, тексты, план

## Разбор запроса на области

Каждое пожелание из брифа разложить по областям и записать, что именно
оно значит для этого сайта. Одна фраза пользователя обычно задевает три-четыре:

| область | вопросы, на которые ответить |
|---|---|
| UI | какие компоненты меняются: кнопки, карточки, шапка, подвал |
| UX | какой путь до заявки/покупки становится короче или яснее |
| Типографика | шкала, гарнитуры, кириллица, длина строки, интерлиньяж |
| Тексты | заголовки, призывы, описания, FAQ — что переписать и почему |
| Картинки | какие нужны, какие заменить, какие убрать |
| Движение | где появления, где наведение, где ничего не нужно |
| WebGL / 3D | нужно ли вообще; см. `engines.md` |
| Навигация | меню, якоря, футер, «позвонить» на телефоне |
| Формы | поля, валидация, согласие, что после отправки |
| Телефон | первый экран, меню, таблицы, формы, цели нажатия |
| Скорость | картинки, шрифты, скрипты, анимации |
| SEO | title, description, h1, alt, семантика |
| Доступность | контраст, фокус, подписи, reduced-motion |
| Структура и страницы | что добавить (опросник, страница услуги), что объединить |

Расшифровка типичных формулировок:

- «дороже» — больше воздуха, меньше элементов на экране, одна гарнитура с характером, крупная шкала, сдержанная палитра (акцент — только если он есть у донора или сайта: «акцента нет» — тоже правило), честные фото, спокойное движение, ни одного дефолтного элемента (стандартные тени, синие ссылки, эмодзи-иконки);
- «современнее» — не набор «актуальных паттернов» (крупный первый экран с одним действием, липкая шапка, карточки без рамок, мягкие появления — это и есть дефолты из каталога `reference/authorship.md`): сначала паспорт донора или сайта, перевод пожелания в приёмы — только через его правила;
- «живее» — движение и фото людей, не карусели;
- «понятнее» — воронка ниже: обещание, доказательство, действие;
- «сохрани стиль» — палитра, гарнитуры, логотип, тон текста остаются; меняется композиция, ритм, качество деталей.

## Матрица «менять / не трогать»

Таблица в `analysis.md` прогона:

| элемент | решение | причина |
|---|---|---|
| основной цвет | не трогать | ограничение брифа; узнаваем |
| первый экран | переработать | h1 не виден на телефоне, кнопка теряется |
| фото команды | сохранить | настоящие, вызывают доверие |
| … | … | … |

Строка без причины не считается решением. «Не трогать» — такая же
осознанная позиция, как «менять», и она попадает в регресс-проверку:
diff должен показать ноль изменений в этих зонах.

## Воронка UX — где трение

Пройти страницу как посетитель с задачей (купить, записаться, позвонить):

| этап | вопрос | типичное трение |
|---|---|---|
| Arrival | понятно ли за 3 секунды, куда попал и для кого это | заголовок про компанию, а не про пользу; шапка съедает экран на телефоне |
| Understanding | ясно ли, что предлагают и как это работает | услуги списком без объяснения; жаргон |
| Interest | есть ли причина читать дальше | нет примеров, цифр, фото результата |
| Trust | почему верить | стоковые фото, нет отзывов/кейсов/лиц/адреса, нет цен даже «от» |
| Decision | всё ли есть для выбора | нет сравнения тарифов; нет ответов на возражения там, где они возникают (у цены, у кнопки) — FAQ-аккордеон один из вариантов, а не ответ по умолчанию |
| CTA | видно ли действие и одно ли оно | три разные кнопки, кнопка ниже сгиба, неясный глагол |
| Conversion | легко ли завершить | длинная форма, нет маски телефона, нет подтверждения, нет «позвонить» на телефоне |

Каждое найденное трение — задача с приоритетом. Воронка обязательна и
тогда, когда запрос чисто визуальный: «сделать дороже» не должно сломать
путь к заявке.

## Тексты

Правила для любого переписанного текста:

- **для читателя сайта**, а не для разработчика: не «адаптивная вёрстка и SSR», а что человек получит и что с этого будет;
- **ничего не выдумывать**: цены, сроки, гарантии, отзывы, цифры, названия клиентов — только с сайта или от пользователя; нет подтверждения — не пишем; место для факта помечать `[уточнить: …]`;
- тон — из существующих текстов (самые длинные абзацы есть в `discovery.md`), если бриф не просит иного; «вы» или «ты» — как было;
- заголовок — про пользу и конкретику, не про «мы — команда профессионалов»;
- призыв — глагол и результат («Записаться на пробное», не «Отправить»);
- один абзац — одна мысль; списки для перечислений; без восклицаний, без «уникальный», «инновационный», «лучший» и без тройных перечислений ради ритма — это и есть «AI-копирайтинг», который слышно;
- FAQ — из реальных возражений (цена, сроки, гарантия, «а если не подойдёт»);
- оговорка «демо» (демо-сайт, условные цены, работы из открытых коллекций) — рядом с действием, которое она касается (у заявки, у цен или одной строкой на первом экране), и в подвале; убирать россыпь сносок под каждой секцией, а не саму оговорку;
- тексты интерфейса (ошибки, пустые состояния, подтверждения) — скилл `design:ux-copy`.

Переписанные тексты показывать пользователю парами «было → стало» в отчёте.

## Приоритеты

| приоритет | что | примеры |
|---|---|---|
| P0 | сломано | ошибка в консоли ломает меню; форма не отправляется; горизонтальная прокрутка на телефоне; битые картинки; шрифт без кириллицы |
| P1 | крупная проблема UX | h1 и кнопка ниже сгиба на телефоне; путь к заявке неочевиден; нет «позвонить»; шапка 30% экрана |
| P2 | крупная визуальная | язык дизайна не соответствует запросу; первый экран; сетка; типографика; картинки |
| P3 | тексты | заголовки, призывы, описания, FAQ |
| P4 | движение | появления, наведение, 3D, микровзаимодействия |
| P5 | полировка | отступы, иконки, тени, мелочи в состояниях |

Порядок работы: P0 → P5. Зависимости внутри: дизайн-система (переменные)
раньше любого UI; тексты раньше подгонки вёрстки под них; картинки раньше
секций, где они стоят; 3D и движение — когда вёрстка уже не двигается.

## План — формат

В `analysis.md` прогона после матрицы и воронки:

```
## План
| # | P | задача | область | чем делаем | чем проверяем |
|---|---|---|---|---|---|
| 1 | P0 | меню на телефоне не открывается (ошибка в menu.js:42) | mobile | правка обработчика | runtime --viewport mobile --click .burger |
| 2 | P1 | первый экран: h1 и кнопка на телефоне выше сгиба | hero, mobile | вёрстка hero через токены | shots mobile-first, глазами |
| 3 | P2 | шкала и воздух по референсу | ui | tokens.css, секции | verify.mjs, diff, глазами |
```

Те же задачи — в журнал `state.mjs add`, чтобы статусы жили отдельно от
плана. Каждой задаче заранее назначить проверку: без неё задача не
закрывается.
